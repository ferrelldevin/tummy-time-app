# Hosting questions for ODU IT and the CS systems group

Internal working document for the lab. It is the list behind step 1 of Block 8 in [build-plan.md](build-plan.md). It makes no promise to anyone and states no answer we do not have. Facts about ODU below are marked **unconfirmed** unless ODU told us.

Why this list exists: the app's home is ODU servers ([ADR 0007](adr/0007-hosting.md)), and nothing about the lab's server is known for sure. The packaging (Docker Compose with a Caddy proxy, PostgreSQL and two database users) assumes things that ODU may not allow. Each question says why we ask and what changes in `infra/` depending on the answer. A temporary off-campus test site with sample data keeps the work moving while ODU answers; it is not a place for real families' data. For what has been run so far: the production files were run in Docker during the Block 8 review, with a test certificate for `localhost`, in one container. Nothing has been run on a real server or on an ODU machine, and nothing has been run with Podman ([security review](security-review-stage-a.md)).

What is known so far, **all unconfirmed**: the CS Systems Group's site lists a research server named `handson-web.cs.odu.edu` that may be the lab's. Personal web space (`~/secure_html`) cannot run this app. Which database the department offers has been reported as MySQL; nothing says the lab server must use it.

Send the questions in the order below. The first three decide whether the rest matter.

| # | Question | Why we ask | What changes depending on the answer |
|---|---|---|---|
| 1 | What machine would the app run on, and who runs it? Is it `handson-web.cs.odu.edu`, a virtual machine, or a shared server? | The lab's server may not be the one we guess. Who runs it decides who we call and who can change settings | Names go in the "who to call" table of [runbook.md](runbook.md) (section 24). A shared server means no root access, which affects everything below |
| 2 | Are containers allowed (Docker, or Podman)? If so, may we run our own images, and as which kind of user? | The whole production setup in `infra/docker-compose.prod.yml` is containers. [ADR 0007](adr/0007-hosting.md) says to document a plain Node service if they are not allowed | **Yes:** use the existing files; check whether rootless Podman needs changes to `read_only`, `cap_drop` and the compose syntax. **No:** write a plain Node service setup (a systemd unit for the API, static files served by whatever web server ODU provides, the same environment variables) and a new ADR. The deploy script would be rewritten, not adapted |
| 3 | Which database software is offered, and can we run our own PostgreSQL? | [ADR 0008](adr/0008-postgresql-and-database-users.md) chose PostgreSQL 16 or 17. The department's service has been reported as MySQL (unconfirmed) | **Our own PostgreSQL in a container:** nothing changes. **A PostgreSQL service ODU runs:** the two database users must be made for us, `infra/db/init-roles.sh` becomes a request to them, and the database port cannot be hidden by us, so we ask for access from the app's machine only. **MySQL only:** reopen the ADR; the schema file and migrations are rewritten (three checks use PostgreSQL features) |
| 4 | How are HTTPS certificates issued for a campus site? Who orders, installs and renews them? Which domain name would the app have? | Caddy gets and renews its own certificate on the test site. ODU may issue certificates itself | **ODU gives us certificate files:** mount them into Caddy and use `tls /certs/...` in `infra/Caddyfile`; renewal becomes ODU's process, which needs a runbook line. **ODU ends HTTPS on its own proxy:** Caddy serves plain HTTP behind it (`auto_https off`), and the number of proxies in front of the API becomes 2: `API_TRUST_PROXY_HOPS` changes and Caddy must trust their proxy address, or the rate limiter sees the wrong address. **Caddy may get its own certificate:** nothing changes, but ports 80 and 443 must reach it from the internet |
| 5 | Is there already a reverse proxy or load balancer in front of campus servers? What address does it show our app for each visitor, and in which header? | The sign-up and sign-in rate limits are per visitor address and depend on reading the true address from exactly the right number of proxy hops ([threat model](threat-model.md) #15b) | Sets `API_TRUST_PROXY_HOPS` and Caddy's trusted proxy list. Getting it wrong either shares one limit across all visitors or lets a visitor escape the limit |
| 6 | Who patches the operating system and the container runtime, how often, and how are we told about a restart? Who patches the images we run (we rebuild them)? | [Threat model](threat-model.md) #27, "unpatched server", is an open question. Images need rebuilding for security fixes even when the machine is patched | The answer goes in the runbook. If ODU patches the machine and not the containers, we need a routine for rebuilding and redeploying, and someone who owns it |
| 7 | What backup service does the server have? Is the database or a Docker volume covered, how often, how long are backups kept, and where are they stored? Can we take our own database dump and have a copy kept off the server? Who may read backups? | Backups must be off the app's own disk ([threat model](threat-model.md) #26) and are not encrypted by our scripts today. Retention (30 days) is a proposal in [data-map.md](data-map.md) | **ODU backs up a database service:** our daily `infra/backup-scheduled.sh` may be extra or unnecessary. **Nothing offered:** we need a second disk and an off-server, encrypted copy, and someone who holds the key. The answer decides the open decision on backup encryption |
| 8 | Where may we store a secret such as the sign-in key (`CODE_LOOKUP_SECRET`), and where may its separate backup live? Who at ODU can read the server's files and environment? | If that key is lost every family code stops working; if it leaks, an attacker with a database copy can test guesses ([runbook](runbook.md) section 17). It must live apart from the database backup | Decides where the key and its backup are kept and who can read them. If administrators can read everything, [data-map.md](data-map.md) already says that is why nothing in the database identifies a person, but the key is still the thing to protect |
| 9 | What security review, scan or approval does ODU require before an app goes live on campus? Is a vulnerability scan run against the site, and by whom? | Block 8's card says to do any review or scan before going live and to add it to the runbook | The requirements become a checklist in the runbook and may add work before launch. Findings from the stage gate review (ASVS Level 1) may already cover part of it |
| 10 | Does ODU require specific standards for campus-hosted apps (web standards, accessibility policy, logging, retention of logs, single sign-on)? | The build plan lists this as not yet known. Our logs deliberately hold no network address ([data-map.md](data-map.md), "In logs"), and caregivers will not have ODU accounts | A required log of visitor addresses would conflict with the data map and needs a decision by Devin and Dr. Gupta before it is done. Any accessibility standard is checked against our WCAG 2.2 AA work |
| 11 | May the server send email, and through which service? (Only if the chosen sign-in method needs email, which is not decided: Block 10.) | Email sign-in needs a mail service behind the sign-in seam | None today. Records the answer so Block 10 does not start cold |
| 12 | Where can lesson video live, and what limits apply (storage, bandwidth, formats, captions)? May video be served from our own server, or must it go through ODU's video service? | Video is in Block 12. Our security policy allows media only from our own server, not outside hosts, and the web app's size budgets assume no video in the first load | **Our own server:** disk and bandwidth need sizing and nginx may need range-request settings. **ODU's service:** the content security policy in `infra/nginx-security-headers.conf` needs a reviewed exception for that one host, which Devin must approve |
| 13 | Who is the contact for outages and who for requests, and how are they reached out of hours? | The uptime check can only alert someone once we know who ([runbook](runbook.md), section 21) | Fills the "who to call" table. Decides how `infra/healthcheck.sh` raises an alert |
| 14 | Does the recruiting clinic, or any part of the system, fall under HIPAA-covered rules at ODU? | Raised in the [threat model](threat-model.md) open questions. If so, a compliance review comes before real users | May add requirements on hosting, logging and access. This is a question for Dr. Gupta and ODU compliance more than IT; ask IT only to point us to the right office |
| 15 | May we run a temporary test site off campus with sample data only while we wait? Is there a rule about hosting a university project elsewhere? | Devin approved temporary staging; the ADR says it is deleted when the campus site is live | If ODU objects, demos wait for the campus server or run on a laptop. If it is fine, the test site uses the same files with `SITE_BANNER=test` |

## What to do with the answers

- Write each answer next to its question, with who gave it. Mark anything someone only said out loud as "told, not in writing".
- Anything that rules out part of the stack goes to Fable to revise the ADRs and the Block 8 card ("Stop and ask if" on the card).
- Update the runbook sections the answers touch, and mark them honestly as not yet practiced until someone has done them on the real server.
- Do not put names, email addresses or phone numbers of ODU staff in this repo. Keep them in the private contact list the runbook points to.
