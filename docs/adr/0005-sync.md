# 0005: Sync rule

Status: Proposed (Nov 10, 2026).

## Context
A caregiver logs tummy time on one phone and expects it on another. Phones go offline. The next student must be able to reason about the rule.

## Decision
- The server is the source of truth.
- The phone creates each entry's ID (a random UUID), saves the entry locally first, and queues it in an outbox. Sending the same write twice is harmless.
- The server stamps every write with the next number from one counter (`rev`). A phone asks for "everything after rev N".
- If two phones change the same entry, the last write to reach the server wins.
- Deletes are marked, not erased, so they sync too. Account deletion erases for real.
- Phones pull on open, on return to the foreground, and after the outbox empties. No live push.

## Options not taken
- **Live push (WebSockets).** More to host and secure, and nobody has asked for instant updates.
- **Merge-based sync (CRDTs).** Solves conflicts that a tummy time log will almost never have, at a high cost in complexity.
- **Comparing phone clocks.** Phone clocks are wrong often enough to lose data.

## Consequences
- Two offline edits to the same entry: one is lost. Accepted for this kind of data.
- A second phone sees changes when it opens or refreshes, not instantly.

## Reopen if
- The client wants caregivers to see each other's entries live.
- Entries gain fields where losing an edit would matter.
